# Технические основания и точные настройки

[Назад к инструкции](../README.md)

## Как выбран профиль

В `nand_support_list_20221202.ini` из исходного пакета строка `[intel] Flash013` описывает `PF29R01T2AMCTH1`, B17A, 1024 Gb. Написание с R сохранено из базы. На корпусе читается `29F01T2AMCTH1`.

База указывает два CE в корпусе, один LUN на CE, четыре Plane на LUN. В нашем Read ID отвечали CH0/CE4 и CH1/CE4. Поэтому в конфигурации прошивки **CHNum=2, CENum=1, BankNum=2**. Это согласованные величины: один отвечающий CE на каждом из двух каналов.

Сохранённая геометрия: CHNum=2, LunNumPerCE=1, PlaneNumPerLun=4, BlockNumPerLun=2016, PageNumPerBlock=2304, SectorNumPerPage=32, Hdr4BLenPerPage=16, FullPageNum=18592, LunBlockShift=11. Параметры памяти сверялись с выбранной строкой базы. Дополнительные тайминги платы наугад не менялись.

Сохранены `DL_MODE=1`, `FW_UPDATE=0`, `PROGRAM_EFUSE=0`, `RUN_BURNIN=0`, `0xc00_1_LLFMode=1` (Force Inherit DBT). Это описание успешного опыта, а не рекомендация наследовать таблицу дефектов на любом другом SSD. В нашем журнале наследование ODBT завершилось успешно.

В успешной сессии SSDMP записала LOW_POWER=0xFFFF47E5 вместо исходного 0xFFFF47F5. Это изменение программы, а не вручную подобранная настройка. Скрипт подготовки сохраняет исходное значение пакета.

## Откуда карта банков

Статический анализ именно указанного SSDMP.exe:

- `ParseIdToGetBankMapping` — 0x1408A0E10;
- `UpdateBankSettingToConfig` — 0x1408CF590;
- `UpdateFlashParameterToConfig` — 0x1408AC3B0.

Алгоритм нумерует отвечающие банки с чередованием каналов, затем заполняет оставшиеся места. Для исходной конфигурации воспроизведены все четыре исходных DWORD. Для CH0/CE4 и CH1/CE4 получаются:

```text
CH0, CE0..7: 2 4 6 8 0 10 12 14
CH1, CE0..7: 3 5 7 9 1 11 13 15
DWORD, little-endian:
08060402 0E0C0A00 09070503 0F0D0B01
```

Это объясняет прежние CH/CE FAIL: штатный профиль ожидал CH0/CE4, CH1/CE0, CH0/CE6, CH1/CE2. Ошибка соответствия сама по себе не доказывала физический дефект памяти.

## Почему нужен PAR_1 и отдельное имя INI

`CompareId` (0x140899300) обнаруживал пустую строку ожидаемого ID и завершался с `No valid flash id` до сравнения банков. Загрузчик 0x1407A8970 читает `TEST_PARAMETER/PAR_1`, отбрасывает первые три символа и убирает пробелы. Штатная запись 0x14086EEF0 использует префикс `ID:`.

Рабочая строка:

```ini
PAR_1=ID: 89 C4 08 32 A6 00 00 00
CHECK_FLASH_ID=1
CHECK_FLASH_ID_LEN=6
```

Выбран отдельный пользовательский файл `intel120_id.ini` вместо шаблонного имени `config_6531.ini`. `X64_Debug/Setting.dat` содержит ссылку на профиль. У двух имён одинаковая длина: подготовительный скрипт меняет только соответствующие ASCII-байты, не структуру записи. Оригинальный INI остаётся на месте.

`DEBUG_MODE=1` включает диагностические журналы. Скрипт ограничивает конфигурацию DUT0 и устанавливает `AUTO_START_TEST=0`. В нашей удалённой сессии на ноутбуке для запуска из SSH временно использовали штатный `AUTO_START_TEST=1` после отдельной проверки устройства; затем отключили. В инструкции предусмотрен ручной Start, поэтому автоматический запуск намеренно не воспроизводится.

## Выход из сервисного режима

После MP Pass прямой ATA IDENTIFY всё ещё возвращал REALTEK_RL6531, FW 3.AAE, 2303 сектора. Это реальные сведения устройства, а не только кэш Windows.

По коду `RtsAtad.dll`:

- `RaGetFWMode`: 0 → `normal mode`, 1 → `llf mode` (декодирование около 0x180459704);
- `RaSetFWMode` → 0x18045DDE0 → 0x180440C20 → 0x180472BE0;
- команда выхода: ATA command **FC**, feature **04**, sector count **00**, device **E0**, без данных, без 48-bit флага;
- проверка режима: ATA command **FC**, feature **03**, device **E0**, 48-bit флаг, без данных.

Использован IOCTL_ATA_PASS_THROUGH 0x4D02C. [Описание структуры ATA_PASS_THROUGH_EX от Microsoft](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntddscsi/ns-ntddscsi-_ata_pass_through_ex).

После SetFWMode(0) Windows вернула успех, ATA status=0x50, error=0x00. Немедленный GetFWMode всё ещё вернул sector count=1; IDENTIFY и перезапуск устройства не дали 120 ГБ. Только после последующего физического переподключения M.2 появился рабочий диск.

Мы **не доказали**, что SetFWMode(0) необходима после каждого успешного MP, и не установили отдельно вклад этой команды и снятия питания. Поэтому обычное выключение с подключённой батареей не называем доказанным полным обесточиванием, а принятую команду — доказанным немедленным выходом из LLF.

[Exit-Llf.ps1](../scripts/Exit-Llf.ps1) — публикуемая версия проверенной команды с явными параметрами выбора диска. По умолчанию только проверяет цель; для отправки нужен `-Apply`. Она предназначена исключительно для совпадающего состояния REALTEK_RL6531 / SATA / 1 179 136 байт **после MP Pass**, при закрытой SSDMP. Это не прошивальщик и не универсальный ремонт.

```powershell
# Сначала посмотреть фактический номер и serial через Get-Disk.
# Пример с условным serial — заменить своими данными, не копировать буквально:
.\Exit-Llf.ps1 -DiskNumber 0 -ExpectedSerial 'YOUR_SERVICE_SERIAL'
# Только после сверки и успешного MP:
.\Exit-Llf.ps1 -DiskNumber 0 -ExpectedSerial 'YOUR_SERVICE_SERIAL' -Apply
```

Скрипт имеет проверки serial, размера, SATA, модели, отсутствия загрузочной роли и повторную проверку открытого дескриптора. Публичная оболочка адаптирована для параметров другого экземпляра и проверена синтаксически; на аппаратуре выполнялась исходная версия той же команды для нашего конкретного диска.

## Полная проверка объёма

После появления 120 034 123 776 байт SSDMP закрыта, её автозапуск отключён. Целевой SSD оставался RAW. Загрузочный USB-диск исключён по интерфейсу, serial и IsBoot/IsSystem.

Наш C#-тест записывал блоки до 4 МиБ. Основа — псевдослучайный буфер; первые 8 байт каждого 512-байтового сектора заменены его абсолютным байтовым адресом. Сначала записан **весь** диапазон, вызван Flush(true), закрыт дескриптор, затем устройство открыто заново и весь диапазон прочитан с побайтовым сравнением. Это выявляет адресное наложение, которое могло бы остаться незаметным при немедленной проверке каждого только что записанного блока.

Результат: **PASS, 120 034 123 776 байт, 2863,7 секунды**. [Полный журнал](../evidence/verification.txt) содержит UTC-время; serial заменён на `[TARGET_SERIAL]`. Это одна проверка ёмкости и целостности, не испытание ресурса или сохранности данных спустя месяцы.

Сначала запись шла около 276 МБ/с, после примерно 47 ГБ снизилась примерно до 30–40 МБ/с. Причина снижения отдельно не исследовалась; называть её доказанным перегревом или конкретным типом кеша нельзя.
